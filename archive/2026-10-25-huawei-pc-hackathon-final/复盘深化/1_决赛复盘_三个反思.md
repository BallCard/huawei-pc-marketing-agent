# 决赛复盘 · 三个反思

- 复盘日期：2026-10-26
- 对象：ZJUshaaa / PC-Studio · 华为赛道决赛（74.22，第 5 名，二等奖）
- 关联：[赛题评分对照 A3 一页纸](2_赛题评分对照_A3一页纸.md) · [竞品证据档案](3_竞品证据档案_四队.md) · [下次比赛 Checklist](4_下次比赛Checklist.md)

本文是赛后讨论沉淀的三条反思，每条给「结论 → 证据 → 一句话教训 → 再战行动」。证据以文件与数字为准，不依赖对话记忆。

## 反思一：产品观重前端，写作方法层过薄

**结论**：后端不是没写，而是全部花在"防错"上；真正的"写作方法"只剩薄薄一层。护城河是"不出错"，不是"写得好"。

**证据**

- 代码分布：`src/mvp/web/`（前端）13,250 行（css 6,809 / html 1,642 / js 4,799），`src/mvp/*.py`（后端）4,880 行 / 22 文件——前端是后端的约 2.7 倍。
- 时间分配：10-23 之后改动前端 5,013 行 vs 后端 2,786 行；60 个提交累计 churn：frontend +17,288 / backend +6,713 / docs +2,207 / other +7,283。越接近截止日，提交越集中在展示层打磨。
- 写作资产规模：`prompts/compose.md`（9,444 B）几乎全是约束（不得超字数 / 不得新增事实 / 条件必须保留 / 数字与报价进程序检查）；写作方法只有 11 个获准样板（`config/marketing_templates.yaml`，来自 adquan/digitaling/admen 广告案例）+ 6 条创作方法（`creative_methods.yaml`）+ 8 组平台风格正反例（`style_examples.yaml`）。
- 修订上限：初次流程 `pipeline.py:791` 明确"按具体问题定向修订（最多一次）"；`continue_review`（`pipeline.py:852-970`）是"一条指令 → 一次重写 → 复审"。交互上没有"编辑会话"（无 diff、无局部重写、无多轮记忆）。

**一句话教训**：我们打磨的是"可信"，不是"好读"；评委要找的"内容吸引人"那一层是空的。

**再战行动**：补一层内容方法资产（20–50 篇真实可发稿拆解 → 钩子/结构/读者价值库），把 compose 从"约束"升级为"约束 + 前置参照"。

## 反思二：赛题破题偏差——把赛题答成了"可信工作台"

**结论**：方向切题（自研 Agent / ima / 合规都做了，见 `notes/competition-fit-review.md`），但对**分值权重**理解偏差：把最稳的 40 分底座（事实 20 + 合规 5 + 自研提示词 15）当成亮点讲，把最该证明的 35 分内容侧（场景理解 20 + 软文质量 15）留白。

**证据**

- 评分表（手册第 9 页）：业务场景理解 20 / 产品事实准确性 20 / 图文生成与图片引用 15 / 平台适配与软文质量 15 / 自研 Agent 与提示词 15 / 功能完成度与体验 10 / 合规与安全 5。统一测试任务明确要求"**同一产品**更换人群或业务场景""**同一任务**更换平台"。
- 展示页 `output/showcase-offline/showcase-functions.html`：13 个功能点、3 条 band、可点击剖面图；现场点法"每次点击只回答一个评委问题"——导览逻辑，不是论点逻辑。
- 收束句原文："我们做的不是一个'会写'的工具，而是一条把事实、判断和经营动作接起来的工作链。"——这就是把赛题理解成"可信工作台"的物证。
- 三个预置案例（`output/showcase-offline/demo.html`）同时换了人群和平台，评委无法分开验证"换场景切入点变"与"换平台结构变"两个判据。

**一句话教训**：读评分表，别读自己的想象；题读了不算破题，按分值的权重布置才算。

**再战行动**：以"同一产品 × 3 人群 × 2 平台并排对照"作为标准演示素材，直接对应统一测试任务。

## 反思三：自信与完美主义——用工艺代替论证，在安全区打转

**结论**：过度自信表现为"以为前端做好看 = 高大上"，以及"想做完整产品"的完美主义把力气横铺到所有功能，而没有纵切到核心链路。

**证据**

- git churn 显示后期提交集中在展示层（换封面文案、调海报比例、Reframe showcase），每一笔都像进步，但都没有移动评分表上的内容侧分值。
- 两个一等奖各只有一句话主张 + 一个硬数字：稿研"376 篇候选 → 102 篇精读 → 14 篇公众号深度蒸馏"（复赛录像，见 `output/first_prize_review/index.html`）；华章有据"680 个自动化测试全绿" + LangGraph/SSE/WAL 工程证据。对比之下，我们的页面有 13 个功能、没有单一数字。
- 我们没有留任何"文章质量"证据：无同一产品换人群的成稿对照、无通用模型盲评、无人工评分/修改量/可发布率。

**一句话教训**：完美 = 一条链路无懈可击，不是所有功能做圆；安全区的信号是"连续提交都集中在确定能做好、但分值最低的事"。

**再战行动**：展示只留一个画面（同题三稿并排 + 点句回原文）；每周问一次"这周的动作在移动哪一分"。

## 客观校准（不被反思误伤的部分）

- 证据链是全场唯一做成了完整闭环的：逐字段引用 + 条件传递 + 规则检查 + 独立评审 + 定向修订后复审 + 版本/审查记录。byai 的 readiness 接口自认 `semantic_verification=not_implemented`；门店助手线上 22 个任务 0 个通过核验；MateQuill 的 audience 只敢标 `editorial_hypothesis`。
- 提示词体系是"自研"的实打实证据：12 个提示词文件 + 7 个规则/方法 YAML（platforms / compliance / scenes / templates / methods / style…），直接对应赛题"自研 Agent 与提示词 15 分"。
- 测试底座真实：197 Python + 35 前端全部通过（对照三个对手仓库在当前环境均无法收集测试）。
- 前端工程能力是放大器不是错误：三版展示页、离线包、真实工作台的可视化能力是全场最强的之一；错在拿它讲通用功能，而不是讲证据链。

**总结**：代码底子（40 分底座）是真的；失分点不在技术，在"没有把可信翻译成一句主张、一个瞬间、一个数字"，外加缺一层让它"诱人"的内容方法。这次比赛真正的奖品是评分逻辑——已经拿到手了。
